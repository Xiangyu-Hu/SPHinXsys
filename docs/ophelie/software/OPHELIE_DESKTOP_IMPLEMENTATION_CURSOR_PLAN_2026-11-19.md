# 冷坩埚桌面软件实施任务书

日期：2026-11-19  
执行对象：Cursor 与 OPHELIE 开发人员  
目标版本：并行开发 Linux x86_64 / NVIDIA SYCL GPU 与 Windows x64 / SYCL CPU 功能验证版，甲方工况就绪后补齐工程验收

首轮软件里程碑：Linux GPU 与 Windows CPU 分别用现有可运行的回归算例完成真实计算、结果回放和安装包试测。甲方几何的自然对流和机械搅拌算例就绪后，按第 2.1 节和第 7 节完成定性检查与平台验收。

## 1. 交付目标和实施边界

交付**一个冷坩埚桌面软件**。Linux 使用 NVIDIA SYCL GPU，Windows 使用 SYCL CPU。两平台共用同一份算例和求解器源码。两种模式共用一个主窗口、一套项目格式和一条操作流程。Linux CPU 可用于开发对照，随包支持以实测为准。两平台可独立构建与试测。甲方算例正式就绪后接入同一项目与结果接口。软件支持打开或保存项目、加载和替换 STL、查看装配、生成和查看实际粒子、填写带单位的参数、检查输入、运行和停止计算、监控时间步与可用残差，以及在窗口内查看和导出结果。已安装 ParaView 时，结果页支持一键打开。

采用 **Qt 6 Widgets + VTK + CMake** 开发桌面界面。采用 **独立 OPHELIE 求解器进程 + 版本化 JSON + NDJSON 运行事件 + VTK/CSV 文件**作为界面与求解器的边界。以当前 SPHinXsys OPHELIE 分支上基于甲方几何开发的程序为产品求解器基线。先在实际工作树中定位该程序、几何入口和编译目标，再接入甲方两套工况预设，统一配置、预处理、运行和结果接口。按里程碑拆分小提交，登记基线和现有本地改动。保留法国复现算例及其调用方式作为回归。开发和打包可在隔离的本地分支或工作树进行，按团队已有流程管理提交。

本版使用规定运动桨壁、现有 WCSPH 及热流动路径。水冷管作为装配展示，允许生成单独的展示粒子，求解体和接触关系列表中不包含冷却管。熔体侧壁和底部是否使用等效冷却，由运行模式与已确认的热边界配置决定。等效边界的系数与环境温度有独立来源记录。首版范围覆盖已经验证可用的顶面模式和熔融暖态工况。管壁涡流、管内水流、全实体线圈导体求解、冷料熔化、明显自由面变形及远程计算另立任务。

开发端使用 SPHinXsys 源码和所需工具链构建 OPHELIE 求解器。客户侧安装软件即可获得桌面程序、对应平台编译好的求解器、必需的运行库和两个示例项目，无需另装完整的 SPHinXsys 源码、开发库或编译工具链。保留现有代码的正常链接方式，按实际运行依赖确定打包范围。

首轮定性短跑允许使用明确标注的开发参数、受控温场或热源，验收依据是甲方装配、实际粒子、边界行为和合理的流动响应。正式物理验收使用经确认的物性、实验边界和验收指标。三维窗口示意、真实短跑通过和实验结果对照通过分别记录。

### 同一项目内切换自然对流和机械搅拌

主窗口的「物理设置」提供唯一的模式控制 **「启用机械搅拌」**。状态栏从该开关显示「自然对流」或「机械搅拌」。新建通用项目默认关闭。导入搅拌桨 STL 时先显示模型并提示是否启用，用户确认后才进入搅拌模式。导入冷却管、热电偶，或在几何树显隐任何零件，均不改变求解模式。

| 状态 | 界面与计算行为 |
|---|---|
| 开关关闭，未导入桨 | 显示自然对流。使用液腔、共用热流动与电磁设置 |
| 开关关闭，已导入桨 | 保留 STL 和之前的搅拌设置，装配树标记「仅预览」。桨不扣除液体体积、不生成求解用桨壁粒子，也不参与接触或扭矩计算。视窗默认隐藏该参考件，可手工显示。此状态的物理含义是无桨的自然对流 |
| 开关打开，桨有效 | 在同一界面上展开桨轴、转速、旋向、启动斜坡及初始桨角。校验几何、浸没、间隙和转速后，生成含移动壁面的求解粒子，并在结果页显示实际可用的搅拌统计 |
| 开关打开，缺少有效桨 | 提示导入或修复搅拌桨，校验失败，阻止生成求解粒子和启动计算。删除已启用的桨时提示用户重新导入或明确关闭搅拌 |

甲方原始自然对流、机械搅拌装配仍作为**同一软件内的两个示例项目**提供，分别预填各自的 STL 与测点，开关状态也预先保存。用户在当前项目切换开关时，只切换搅拌求解状态，其他部件和参数来自当前项目。若要使用另一套甲方热电偶或装配，应明确打开对应示例或手动替换部件。首版关闭搅拌表示求解域中移除桨。若后续需要模拟「桨仍浸在熔体里但停止转动」，另加静止桨壁模式。

切换只对下一次准备和运行生效。已启动的任务使用独立的生效配置，其结果按原模式打开。新模式根据计算几何和物理体列表核验粒子缓存。包含桨的预处理与无桨预处理不可混用；如果已有完全匹配的目标模式缓存，可以直接复用。

## 2. 开工顺序和阶段验收

两条工作可以并行。软件工作按 **M0 双平台基线 → M4 桌面工作流 → M5 Linux GPU / M6 Windows CPU 打包试测**推进，先使用已有能实际推进的回归算例或小型自备算例。M1、M2 按甲方两案各自的就绪时间推进。现有法国回归可选用已实测通过的短跑路径，尚在修复的物理模式单独记录。M3 四环电磁源独立推进。甲方算例接入后，使用正式接入的输入再做双平台回归与客户验收。

| 阶段 | Cursor 要完成的功能 | 进入下一阶段前检查什么 |
|---|---|---|
| **M0 双平台基线与试编** | 固定同一份求解器源码和可跑的回归输入。在 Linux 编译 GPU 目标，在 Windows 确认 SYCL CPU 枚举、最小 kernel 和实际 SPHinXsys 回归目标，验证 Qt 嵌入 VTK | 两边各交实际后端、设备、构建日志和短跑结果。甲方工程模式可在独立工作树继续开发 |
| **M1 自然对流命令行闭环** | 在统一配置中先接入关闭搅拌的甲方项目。接入装配变换、参数化液腔和壁面、粒子预处理、静水和受控温差短测。实现最小 CLI、进度和结果索引 | 在 Linux 上从客户 STL 和配置生成粒子，随后用这份粒子在 NVIDIA GPU 上短跑并写出可读 VTP/CSV。核对静水、浮力方向和边界泄漏 |
| **M2 搅拌命令行闭环** | 在同一配置中接入可选的甲方偏心桨轴和测点、运动壁面、初始排除体、转速与旋向。完成至少一整圈的规定桨运动的等温短跑，再接热运行。检查近壁间隙和扭矩统计路径 | 同一 Linux NVIDIA SYCL 后端读取甲方有桨项目的实际粒子，记录转轴、转速、扫掠、桨旁流体响应和边界行为。若申报扭矩可用，确认取矩点、符号、单位和统计范围，且结果来自真实壁面作用力 |
| **M3 四环电磁源** | 从 STL 解析四环尺寸并先接中心线，再实现有限截面积分。接回现有 A_coil、熔体 E/J/Q 和空间热源传递 | 用同一电流做轴线场、截面积分加密和两种源模型对照。核对热源分布、积分功率、EM 到流体的实际入热。此阶段可与 M1、M2、M4 并行推进，正式电磁演示需通过本阶段验收 |
| **M4 桌面工作流** | 先接入已有可运行的回归配置，打通真实求解。M1、M2 的甲方工况就绪后逐个接入，复用相同配置、命令与输出契约。实现项目、STL 装配、参数表单、粒子查看、运行监控、结果、ParaView 联动 | 在同一窗口完成两种模式的「打开项目 → 检查 → 生成粒子 → 运行 → 查看与导出 → 重新打开旧结果」，并在同一项目实测开关往返切换 |
| **M5 Linux GPU 打包与验收** | 制作 Linux 安装包与依赖清单，先用回归预设按第 7.4 节实测。M1、M2 就绪后纳入两份甲方预设 | 干净 Linux 环境确认实际 GPU 计算和桌面结果回放。甲方两案可用后补齐工程验收项 |
| **M6 Windows SYCL CPU 打包与验收** | 与 M5 并行。用同一份来源构建 Windows SYCL CPU 求解器和 Qt/VTK 界面，复用 CLI 和结果接口。按第 7.5 节试测 | 无独立 GPU 的干净 Windows 环境通过回归计算和桌面工作流。甲方两案可用后补齐 Windows 工程验收项 |

M0 具体查找起点：

- 先在当前工作树确认甲方 STL 导入、杯腔、坐标变换和预处理等工作已落在哪个程序和配置入口。记录实际源码与目标、分支、Git SHA 和相关未提交改动。若现有甲方入口只覆盖一套工况，沿用其通用路径接入第二个甲方配置。
- `test_3d_ophelie_french_natural_convection_frozen_q`、`test_3d_ophelie_french_stirring_em` 以及实际生效的预处理目标。若目标已改名，记录现行目标和路径。
- `OphelieFrenchReducedCaseParams`、自然对流的玻璃圆柱与开口杯壁 shape、`refreshFrenchReducedCoilStack`、EM 热源传递函数及实际采用的 STL/旋转运动模块。
- SYCL 队列和 NVIDIA 设备选择、Linux CMake 构建目标、当前 VTP/CSV 格式、实际 GMRES 与黏性迭代输出。
- 软件接口优先包装已有代码。从局部修改入手，只有几何、后端或参数确实硬编码时，才提取当前工况所需的共享逻辑。CLI 的单个前端依实际编译条件可启动不同后端程序。每个提交记录改动和测试，未通过的能力在界面上据实显示。

### 2.1 首轮两个甲方算例的短跑验收

为甲方自然对流和机械搅拌各建立一份独立的短跑预设。分别记录粒子预处理和流场推进实际使用的后端。若当前预处理在 CPU 完成，可沿用该实现，随后验证主时间推进在指定 NVIDIA GPU 上执行。共享第 5 节的配置与接口。两份预设使用各自的 STL、测点和搅拌状态，即使看起来相似也按实际来源记录。标明预设用途为「功能验证／开发参数」，在运行快照中记录实际液深、初温、热源或温场、边界、物性、粒子间距和转速等生效值及来源。正式模板保留待确认的实验参数。

| 顺序 | 执行与检查 | 首轮通过证据 |
|---|---|---|
| 两案共同准备 | 检查 STL 角色、单位、坐标变换、液位和测点。运行 `validate → prepare`，导出装配和粒子剖面，核对粒子组、体积、边界范围及缓存指纹。水冷管和热电偶按任务书约定参与展示或采样 | 两份可独立复跑的配置与几何诊断。实际流体、壁面和搅拌桨粒子与各自装配重合，流体有桨时扣除初始浸入体积。展示部件不进入求解体和接触关系 |
| 自然对流 1：等温静水 | 关闭搅拌，先用均匀温度做重力与静水短测，检查液面、侧底边界、粒子位置和速度，沿深度采样压力并记录压力剖面 | 有零速初始帧和稳定推进后的结果。检查侧底无明显漏粒，记录压力随深度的趋势以及寄生速度，遇到明显异常先定位边界或初态 |
| 自然对流 2：受控温差 | 复用同一批粒子，优先使用已支持的固定空间温差，或使用能在短跑窗口内建立明确温差的受控热源。选用经过工况核查的顶面模式，并在含重力方向的剖面输出温度、竖直速度及速度矢量 | 结果中温差位置与输入一致，浮力方向正确，可见热区上升及相应回流趋势。若响应尚未建立，延长模拟物理时间或做同配置的等温对照，再结合浮力、边界和黏度诊断 |
| 机械搅拌 1：等温运动壁面 | 使用甲方有桨装配，复核偏心轴、旋向、间隙和浸没。基于角度或实际桨位检查启动斜坡，并在斜坡结束后覆盖至少一整圈的实际转动。实测全周扫掠及桨附近流体速度 | 保存初始、斜坡结束和运行中不同桨相位的结果。桨壁沿正确偏心轴旋转，转速、旋向和扫掠与配置一致，边界无明显穿壁或漏粒，实际流体速度对桨运动有可辨认的响应 |
| 机械搅拌 2：热运行 | 等温短跑通过后，在同一装配和运动检查基础上叠加受控加热，核对温度场、测点和实际入热 | 保存后续热短跑的单独配置和输出。等温短跑的首轮通过条件以运动壁面及实际流动证据为准，定量近壁速度、扭矩和实验温度对比留到后续验证 |

每案至少保存：

- 运行命令、求解器构建版本及后端/设备、STL 哈希、装配变换、`effective-case.json`、`prepared.json` 和粒子统计。
- 实际模拟时长、时间步记录、退出状态和 `solver.log`。已有能力时输出 `events.ndjson`，便于桌面监控直接复用。
- 可重开的帧文件和 `result-index.json`，配置中有效测点的 `probes.csv`，以及一张装配或粒子剖面图和一张流动/温度结果图。搅拌另存实际桨轴、角速度或角度时序。
- 每个检查项的通过、失败或未验证状态及对应证据。若任一工况只完成了装配或粒子预处理，继续定位阻塞，并保持该工况的短跑状态为未通过或未验证。

这两次实际计算形成桌面端首批接入数据和发行短跑预设的基准。允许首轮采用较粗分辨率，记录近壁间隙与粒子间距。若流体响应或几何通过性仍难判定，针对该指标加密复测。用明确标注的演示配置解释首轮温度、速度或功率量级，实验对照按第 7.2 节验收。

### 2.2 Windows 与 Linux 的 Git 协作

**原有 OPHELIE 分支继续作为集成分支。** 两台机器先从同一个已记录的 Git SHA 开工，分别使用独立工作区和构建目录。双平台软件开发使用现有可运行的回归输入，甲方自然对流和机械搅拌预设按各自的就绪时间接入。

1. **在现有 OPHELIE 工作区整理基线。** 先检查当前分支、已跟踪改动和未跟踪文件，找出实际在用的求解器入口、CMake 改动、运行所需配置、可复跑的回归输入和需要留档的任务书。按功能提交，并至少在已有 Linux 环境构建并跑一次回归。记录提交 SHA、构建方式以及当前已通过和待完成的算例。编译目录、运行日志、求解结果、临时脚本和诊断打包文件留在本地。甲方原始几何和物性资料按授权方式单独同步，代码仓库记录所需相对路径和校验和。检查拟同步的提交历史和文件范围后，使用获准的私有远程分支或 Git bundle 同步。
2. **按 Windows 的工作内容选择分支。**

   | Windows 工作 | 分支与同步方式 |
   |---|---|
   | 只试编、跑算例、测试界面或安装包 | 检出原 OPHELIE 集成分支，由 Linux 侧更新该分支。Windows 工作区干净且已配置跟踪分支时，用 `git pull --ff-only` 同步。需要复现某轮结果时，检出该轮记录的 SHA |
   | 需要修改 CMake、SYCL CPU 设备选择、平台路径或打包代码 | 从当前验证的 OPHELIE SHA 建立工作分支，例如 `ophelie-windows`，先在该分支提交并试跑。将通过的提交合回 OPHELIE 集成分支，可以合并工作分支，或在只需要部分改动时逐个选取提交。Linux 若同时做独立的源码改动，也可以从同一基线建立工作分支 |

3. **遇到分支分叉或本地改动时先保留工作。** 若快进同步失败，用 `git status` 和 `git log --left-right --oneline 'HEAD...@{upstream}'` 检查本地改动与分叉。先把要保留的 Windows 改动提交到工作分支，再由集成分支维护者整合。同步和整合过程中避免强制推送或硬重置。
4. **整合后用同一提交复测。** 两边分别用 `git rev-parse HEAD` 核对 SHA，并记录工作区状态、实际构建选项、SYCL 后端、设备和回归输入版本。确认 Linux 使用 NVIDIA GPU、Windows 使用 SYCL CPU，两个安装包在各自平台实际完成时间推进及结果回放。甲方预设就绪后用同样方式复测四个工程验收项。

## 3. 甲方工况与几何预处理

CAD 几何已迁入对应 relax case 的 `data/`（不再放在 `docs/ophelie/software/`）：

### 3.1 装配角色与坐标

| 角色 | 自然对流 | 机械搅拌 | 作用 |
|---|---|---|---|
| 坩埚 | `glass_NC.STL` | `glass.STL` | 壳体展示，用内腔尺寸与液位定义液体域和数值侧底边界 |

导入时确认 STL 长度单位，本批按 mm 解析。以各套坩埚外底轴心为装配原点，保持整套零件的相对位置。若求解器沿用 +Z 向上，推荐将去平移后的 CAD `(x,y,z)` 映射为求解坐标 `(x,-z,y)` 后统一换算成 m。写出可复核的 4×4 变换矩阵，由同一份几何元数据驱动 STL 预览、粒子、热电偶、重力和电磁源。界面显示坐标轴、原点和单位。

甲方杯壳外径约 285 mm，内径约 283 mm，外高约 250 mm，内底高于外底约 1 mm。界面将 **液深定义为从内底到初始自由面的高度**，同时在三维视窗标明液面高程。几何审计表和下述线圈、桨叶高度以外底为坐标原点，两套基准之间按实际内底位置换算。杯壳网格给视窗用。流体体积由内腔、液位和初始浸入件构造，数值边界的厚度按粒子支持范围设定。真实 1 mm 杯壳厚度、数值壁面厚度与等效导热厚度各有独立含义。

机械搅拌的桨轴沿 CAD +Y，相对坩埚轴偏心约 –67 mm（X）。桨轴和旋转相位来自装配或显式配置。桨叶最低处约在外底以上 180 mm，扫掠半径约 65 mm，几何估算最小桨壁间隙约 9.3 mm。热电偶几何下端位于外底以上约 130 mm，自然对流在轴心，搅拌相对坩埚轴偏心约 70.5 mm。实际感温点单独配置。运行前检查最初浸没、全周扫掠、与坩埚的最小间隙和测点位置。对搅拌输出明确规定从哪一端观察旋向，求解器以有符号角速度转换。扭矩绕真实偏心轴计算，记录正负号约定。

水冷部件直接用甲方 STL 的三角面渲染，沿用整套装配的坐标变换，支持单独显隐、透明和剖切。界面将「显示水冷部件」和「启用等效冷却」做成独立设置。热模型启用等效冷却时，在熔体侧的对应坩埚内壁或底面施加，明确记录作用区域、等效换热系数与参考温度及其来源。切换显示不改变求解输入与粒子缓存。

输出坐标和装配诊断 JSON、装配剖视截图和测试输入哈希。线圈和冷却管中已发现少量零面积三角形。原 STL 保留，清理副本记录已清理面数和非流形检查结果。若导入替换件无法识别为当前模板的几何角色，或超出圆柱坩埚/同轴环计算源的支持范围，界面仍可预览，计算前明确报出限制。

| 功能 | 需要的输入 | 产物与验收 |
|---|---|---|

## 4. 四环线圈源与物性参数

### 4.1 线圈结构和实现

以坩埚外底为 0，甲方两套装配的线圈相对尺寸一致。每环内半径约 168.5 mm，外半径约 171.5 mm，中径半径约 170 mm。

| 环 | 轴向区间 mm | 中心高度 mm |
|---|---:|---:|
| 1 | 39.078–119.078 | 79.078 |
| 2 | 129.078–209.078 | 169.078 |
| 3 | 220–300 | 260 |
| 4 | 310–390 | 350 |

1. **同一 STL 驱动预览和源数据。** 预处理按连通分量识别环，输出各环轴线、内外径、上下面、拟合误差、变换和文件哈希。允许人工核对后录入源参数，记录来源。预览页显示环尺寸，计算前检查来源和当前 STL 匹配。
2. **中心线模式。** 给定每环的中心、半径、轴线、段数、相量电流和频率，沿用 Biot–Savart 数学源。支持四环各自高度，处理现有等距堆栈入口时保留旧法国预设行为。先用单环解析轴线场验证位置、方向和单位，再做四环叠加。
3. **有限截面模式。** 以每环的实际径向厚度约 3 mm、轴向高约 80 mm 布置积分采样。复用圆环核，权重归一到每个实体环的总电流，避免把每个采样环当成满电流绕组。初版可用明确标注的均匀截面电流假设。截面积分和圆环分段分别加密，对比轴向场、热源热点、轴向分布和积分功率。报告两种源模式在**相同电流和频率**下的差异。按这些对照和实际成本决定正式预设。
4. **热源送入流体。** 沿用已核实的 E/J/Q 和空间热源传递路径。针对新液腔重建映射域与热源文件，检查粒子运动时的重采样位置、越界统计以及 EM 域积分和流体实际入热的差异。热源结果记录计算是否含熔体自感及数据来源。

实际环的馈电方式、频率、每环电流方向与相位由甲方确认。首版支持两类清楚命名的模式。用规定熔体吸收功率驱动时，保存设定功率、空间热源类型、适用时的归一前功率及归一系数、实际积分入热。启用给定环电流模式时，记录电流为峰值还是 RMS、各环相量、频率和求得的吸收功率。纯规定热源运行时，无电磁求解残差，界面按实际路径显示「未启用」。诊断短跑也可以用固定温场或受控热源，独立注明工况用途。

## 5. 界面与求解器的文件和接口

CLI 名称可以根据现有项目调整，GUI 和命令行必须走同一验证和运行路径。先提交接口和一份可阅读的示例工况，再接 UI。通过版本字段支持后续兼容更新。

```text
coldcrucible-solver info --json
coldcrucible-solver validate --config <case.json>
coldcrucible-solver prepare --config <case.json> --output <prepared-dir>
coldcrucible-solver run --config <case.json> --prepared <prepared-dir> --output <run-dir>
```

| 契约 | 最小内容 |
|---|---|
| `case.json` | `schema_version`、用途、几何和变换、材料来源与参数、热初态和边界、加热配置、搅拌、离散及输出、执行后端。用 `stirring.enabled` 作为计算模式唯一来源，桨 STL 由装配的搅拌桨角色引用。保留独立的配置身份或预设名称供显示，避免再用另一个独立开关派发求解。内部统一 SI，GUI 单位转换只进行一次。项目内用相对路径 |
| `info` | 软件/求解器版本、支持的配置版本、后端、实际可用设备、支持的物理和导出模式，以及后端不可用的原因 |
| `validate` | 机器可解析的检查结果，字段路径、严重级别、错误代码和用户可读说明。GUI 将警告定位到参数或零件 |
| `prepared.json` | 预处理输入指纹、算法/格式版本、生效的搅拌状态和装配变换，各求解体的数量、Reload 及对应可视化文件 |
| 运行事件 | 标准输出逐行 JSON，普通文字日志走标准错误及日志文件。结构化事件至少有开始、阶段、进度、警告、错误和结束。GUI 容忍新增的可选字段和未知事件 |
| `result-index.json` | 运行状态、各帧物理时间、文件、数据体、字段和单位、曲线及 ParaView 入口。帧写完后再更新可读索引，记录真实保存时间 |
| `summary.json` 与 `effective-case.json` | 实际解析参数、求解器版本、后端和设备、精度、退出状态、输入与预处理指纹、使用的物理路径、计时及可用统计量 |

进度事件示例中的数值只用于描述接口。

```json
{"event":"progress","stage":"flow","physical_time_s":0.02,"step":37,"dt_s":0.00052,"dt_kind":"acoustic_substep","wall_time_s":2.8}
```

- 明确 `step` 统计哪一级推进、`dt_kind` 对应声学子步、对流步或其他已实现层级。外层进度按实际物理时间，预处理阶段没有可量化总量时显示忙碌状态。显示当前值、最近区间范围和历史。定期从真实求解路径采样，避免为界面在每个 GPU 子步做同步。
- 残差事件只有实际发生迭代时才发送，包含求解器/方程、物理时间、迭代数、残差定义及归一化、最终值、容差与收敛状态。支持现有 GMRES 和确有证据的隐式黏性路径。未启用显示「未启用」，有效但尚无数据显示「等待数据」。密度偏差和能量不闭合放在各自诊断项。
- GUI 使用异步 `QProcess`，以程序和独立参数列表调用。用可写的独立运行目录解耦旧算例相对路径和软件安装目录。对日志批量刷新。按事件与进程退出共同判定最终状态。
- 先实现可协作的停止请求，例如 stdin 控制消息或每个运行目录内的取消请求文件。求解器在可控边界结束并写出 `cancelled`。异常退出或强制关闭后，保存已完成文件并标记相应状态。首版停止不承诺断点续算。
- 项目保存以实际解析的工况生成独立运行快照。再次运行生成新的目录，旧结果仍能打开。覆盖前确认，复制项目时能将项目依赖的 STL 和物性文件一起带走。
- 交付时记录支持的 `schema_version` 与运行事件版本。新增可选结果允许旧界面忽略。涉及字段含义、必填参数或存储格式变化时，提供迁移或明确错误，不静默套用新默认值。

推荐运行目录：

```text
project/
  case.json
  assets/
  prepared/<fingerprint>/
  runs/<run-id>/
    effective-case.json
    summary.json
    events.ndjson
    solver.log
    result-index.json
    probes.csv
    results.pvd
    frames/
```

## 7. 软件验收、物理验证与发行

### 7.1 软件功能验证矩阵

开发版先在 Linux NVIDIA SYCL GPU 和 Windows SYCL CPU 各通过一次真实回归计算与桌面测试。甲方工况就绪后验收四格，即两平台各测自然对流和机械搅拌。Linux CPU 对照可单独记录。每格记录操作系统、编译工具链、依赖、后端、设备、驱动、精度、输入配置、实际运行时间及产物。只有实测通过才标 PASS。GPU 不可用时应报错，禁止静默使用 CPU 代跑。支持的平台与设备以实测结果为准。

每格最少执行：

1. 安装、打开项目、检查装配、生成并查看粒子、保存项目。
2. 使用一份固定软件审核配置执行真实短跑，核对进度、时间步、可用残差和输出场。
3. 重新打开项目和旧结果，加载实际时间序列、切换字段、导出 CSV/VTP。在同一项目补测「无桨 → 导入桨但未启用 → 启用 → 关闭 → 重新启用」，验证桨的求解体状态、粒子缓存、旧结果标签和缺桨的拦截。验证带中文或空格的合法路径、缺 STL、失效缓存和后端不可用提示。
4. 测试停止和失败时的状态及部分结果保留。至少准备一个带实际求解器的异常输入测试；崩溃等界面异常可用测试进程补覆盖。
5. 有 ParaView 的机器验证打开时间序列，无 ParaView 的机器验证内置结果查看。验证项目目录移动后相对路径有效。

短跑参考应由同一输入、已知软件版本和实际结果形成。验收容差按物理量、精度和 CPU/GPU 差异制定。至少检查同一配方的粒子/几何统计、时间和输出完整性，按模式比对温度、入热和可用的扭矩等关键量。软件运行状态不作为实验准确度判据。

### 7.2 两个工况后续物理验收

| 工况 | 推荐顺序与证据 |
|---|---|
| 自然对流 | 静水/顶面检查 → 固定空间温差与浮力方向 → 加热和热边界的能量收支 → 四环热源和有效物性 → 与甲方测点温度及已提供的流动观测比较。法国 Fig. 8 作为法国基准验证资料 |
| 机械搅拌 | 核对偏心桨轴与运动边界 → 等温短跑、转速和间隙 → 粒径敏感性和可用扭矩 → 叠加温变黏度及热流动 → 与甲方数据比较。硬件一致性和实验通过各有结论 |
| 四环电磁 | 单环/多环场验证 → 中心线和有限截面的同电流比较 → 确认电流/频率或吸收功率的物理定义 → 核查熔体的空间 Q 和实际热输入 → 如要求，更新电导率反馈并验证 |

待甲方确认：单位与液位，探头实际感温点，两个工况的暖态初温及转速和旋向，黏度原始数据及有效温区，其余热物性，环馈电与频率，功率是电源、线圈还是熔体口径，以及热边界的测量或等效参数。软件短跑可先使用独立的演示配置，通过前述输入检查即可；未确认参数不要覆盖待确认的正式模板。

### 7.3 打包和后续升级

- **构建与安装。** 现有 OPHELIE 计算代码继续在当前分支或隔离工作树中编译，按已验证的方式链接 SPHinXsys。交付包只需要桌面程序、已编译的 OPHELIE 求解器、动态运行依赖及其插件、两套示例项目和使用说明。静态链接进入求解器的组件无需再附一份独立库，实际引用的 SPHinXsys 或第三方共享库按发行许可和平台要求随包提供。完整源码、头文件、测试集及开发工具链保留在开发环境。
- **编译机。** 使用现有已验证的 oneAPI/DPC++、Codeplay NVIDIA 后端和 CUDA Toolkit 组合编译，记录准确版本、GPU 架构目标、Ubuntu 版本和构建命令。完整 Toolkit、编译器、CUDA 头文件和构建工具留在开发环境。
- **Linux 交付包。** 包含桌面程序、已编译的 SYCL GPU 求解器、Qt/VTK 运行库与 Qt 平台插件，以及实际用到且可分发的运行库。核对 SYCL 运行库（`libsycl`）、Unified Runtime loader（`libur_loader`）、Codeplay CUDA adapter（`libur_adapter_cuda`）及其依赖。对 Codeplay 2025.2 检查 `libcupti`。依照实际依赖和分发许可决定随包提供或列为单独的运行时安装依赖。记录文件版本、来源和加载路径。
- **NVIDIA 驱动由目标机提供。** 记录最低支持或已验证的驱动、GPU 型号和 Linux 发行版。运行时应加载系统 NVIDIA 驱动提供的 `libcuda.so.1`，避免加载 CUDA Toolkit 的 stub。首版仅声明实测通过的组合。
- **依赖验收。** 分别检查桌面程序、求解器、CUDA adapter 和其他必须的动态加载插件。通过安装后的启动器或应用私有的库搜索路径加载随包库。用户无需手动 `source setvars.sh`。用第 7.4 节在无完整开发工具链的 Linux 目标环境验收。
- **Windows 并行发行。** 先构建 Windows SYCL CPU 验证包。随包核查 Qt/VTK DLL、SYCL 和 CPU 后端运行依赖。按实际依赖确定随包文件和运行时安装前置条件。
- 产品包附两个可复跑短算例、中文安装/快速使用说明、支持平台和已测硬件、已知限制、发行版本和相应的验证摘要。部署包在未装开发环境的目标机做验证。
- 物理实现变动且接口兼容时，独立重编受影响的平台/后端求解器和变动的运行依赖，保留界面构建。物性纯数据更新时替换相应表或预设并更新来源。用户界面或配置契约有变化时更新相应组件。对外以完整版本包交付，保持旧结果可读。
- 每轮提交一份短报告，写明本轮新增和已通过的功能、复现命令、截图/结果、未通过项与下一步。附各工况的实际配置、版本和日志。测试用程序的输出可以验证界面行为，真实求解的通过状态只基于实际运行证据。

### 7.4 用户在 Linux 上怎么测试

按「开发机真实短跑 → 干净目标环境验收发行包」执行。甲方项目尚未就绪时，使用现有真实回归项目做同样的软件流程检查。下列两案命令作为甲方项目就绪后的验收模板。SSH 终端可以先做命令行测试。桌面验收需要能打开 Linux 图形窗口的会话，例如本机 Linux 桌面或已有的远程图形桌面。若目前只有服务器终端，先交付真实 GPU 短跑记录，桌面项在有图形会话的目标机补测。

1. **接收并解压验证包。** 发布时提供实际包名、启动命令、发布的 Git SHA、两个示例目录、驱动和系统要求。包内为每个示例附独立、可写的工作目录或复制说明。建议命令行布局和下面一致。
2. **检查真实 GPU。** 执行 `nvidia-smi`，记录 GPU 和驱动。运行求解器 `info --json`，确认它能枚举到 NVIDIA GPU 与 CUDA 后端。多 GPU 主机按发行说明选定一张卡，并在实际运行日志中核对设备。
3. **先跑命令行。** 分别执行自然对流和搅拌，分别落盘。验收依据为第 2.1 节的粒子与短跑证据、进程退出状态、实际后端和结果索引。对照版本使用同一预设。开发机可以用已有环境定位问题，发行包验收应重新使用干净环境。
4. **再跑桌面。** 用包内启动器打开 GUI，依次打开两个示例，从「检查 → 生成粒子 → 运行 → 结果」各走一遍。检查几何与粒子对齐、GPU 名称和进度，重新打开真实结果。自然对流查看温度/速度剖面，搅拌查看实际桨位与桨旁速度场。试一次停止操作，并确认已生成的帧可回放。显隐水冷部件时，核对热边界选项和已有计算结果保持一致。
5. **在干净目标环境复测。** 使用有兼容 NVIDIA 驱动及图形会话的 Linux 机器或系统镜像，确保没有安装完整的 CUDA Toolkit、oneAPI 和 SPHinXsys 开发环境，按发行说明安装列出的运行时依赖。开全新会话，从发行包原样重复检查设备、两套命令行短跑和 GUI 测试。日志必须同时记录实际 GPU、CUDA 后端和成功推进，`nvidia-smi` 或设备枚举结果只作为环境检查。

按第 5 节约定的接口，发布包采用下面的布局时，可在包根目录执行以下命令。交付前由 Cursor 用真实发行物核对路径、启动方式与示例名称。若求解器需要启动脚本，由发行包提供同名入口。测试前确认当前目录可写。

```bash
set -e
nvidia-smi
./bin/coldcrucible-solver info --json

test_dir=$(mktemp -d ./ophelie-test.XXXXXX)
for example in natural-convection mechanical-stirring; do
    case_file="./examples/$example/case.json"
    prepared_dir="$test_dir/$example/prepared"
    run_dir="$test_dir/$example/run"
    mkdir -p "$prepared_dir" "$run_dir"
    ./bin/coldcrucible-solver validate --config "$case_file"
    ./bin/coldcrucible-solver prepare --config "$case_file" --output "$prepared_dir"
    ./bin/coldcrucible-solver run --config "$case_file" \
        --prepared "$prepared_dir" --output "$run_dir" \
        > "$run_dir/cli-events.ndjson" 2> "$run_dir/cli-stderr.log"
    test -s "$run_dir/summary.json"
    test -s "$run_dir/result-index.json"
done
```

| 测试现象 | 排查与留档 |
|---|---|
| 求解器启动时报缺库 | 对实际 ELF 求解器和 CUDA adapter 分别执行 `ldd`，检查 `not found` 和意外加载的开发机路径。对 GUI 再检查 Qt 平台插件 |
| 驱动可见，求解器找不到 NVIDIA GPU | 检查 CUDA adapter 与 CUPTI，使用 `SYCL_UR_TRACE=-1 ./bin/coldcrucible-solver info --json` 采集运行时加载日志。必要时对短跑使用同一诊断变量并保留 stderr |
| 可以枚举 GPU，启动时间推进失败 | 保存设备、驱动、编译架构、报错和实际生效配置，核查运行库兼容性及设备端代码启动。用同一短跑复测修复结果 |
| 界面可开，两案输出异常或不完整 | 核对 GUI 启动的求解器版本、后端、生效配置、退出状态、运行索引和帧文件。用相同输入复现 CLI，记录是界面、依赖还是求解问题 |

验收记录包含包版本与 Git SHA、操作系统、GPU 与驱动、依赖来源、两个案例的 `summary.json`、`result-index.json`、日志和结果截图。将已实测的发行包识别为 Linux GPU 验证版。Windows 复用同样的证据清单。

工具链与后端依赖参考 [Intel SYCL 部署指南](https://cdrdv2-public.intel.com/834245/dpcpp-cpp-compiler_developer-guide-reference_2025.0-767253-834245.pdf) 和 [Codeplay 2025.2 NVIDIA 后端排查指南](https://developer.codeplay.com/products/oneapi/nvidia/2025.2.0/guides/troubleshooting)。

### 7.5 Windows SYCL CPU 核查与试测

1. **检查 CPU 设备。** 在 Windows oneAPI 开发环境执行 `sycl-ls`。若测试 OpenCL CPU 路径，可在 PowerShell 用 `$env:ONEAPI_DEVICE_SELECTOR = 'opencl:cpu'` 后再次检查。确认目标机器具备兼容的 CPU 运行时。环境过滤仅用于缩小候选设备范围，代码硬编码 GPU 选择器时需要调整设备选择层。
2. **编译 CPU 目标。** 使用可用的 Windows DPC++ 工具链编译同一份 SYCL 源码，探查实际 CMake 选项。CUDA 目标参数（如 `nvptx64-nvidia-cuda`）、直接 CUDA API 和专属链接依赖如有使用，按平台隔离。Windows 目标必须带 CPU 后端可执行的设备代码。算例物理和通用 SYCL kernel 优先复用。
3. **逐级试跑。** 先运行最小 SYCL CPU kernel，再运行一个调用真实 SPHinXsys 求解路径的现有小算例。记录队列的实际设备类型和后端，确认完成时间推进并写出结果。若遇到 CPU 不支持的 USM 能力、精度、子组大小或固定工作组大小，先确认具体限制，再修改相应执行层。小 kernel 通过仅代表 CPU 设备与基础编译链可用。
4. **验证发行包。** 在没有独立 GPU、没装完整开发工具链的 Windows 目标环境，从 Qt 界面启动真实回归计算并打开结果。核对 CPU 运行时依赖和日志。甲方自然对流及搅拌配置可用后复跑并与同输入的 Linux GPU 结果对照，按后端精度和离散误差核对关键量。

参考 [Intel DPC++ 设备选择](https://www.intel.com/content/www/us/en/docs/oneapi/programming-guide/2025-0/device-selection.html)。

## 8. Cursor 第一轮可直接执行的任务

1. **固定源码基线并同步。** 按第 2.2 节整理现有 OPHELIE 工作区，让 Windows 和 Linux 从同一提交开工。Windows 只试编时跟踪集成分支，需要修改源码时切到工作分支提交。
2. **并行试编。** Linux 构建现有 NVIDIA SYCL GPU 目标。Windows 优先核查 SYCL CPU 设备，编译最小 kernel 和一个真实 SPHinXsys 回归目标。记录实际依赖和需要隔离的 CUDA 专属配置。
3. **用现有算例打通桌面。** 复用 CLI，完成项目打开、装配与粒子显示、启停、日志和结果回放。两平台独立制作并试测开发包。回归算例标明用途，软件通过状态以真实计算记录为依据。
4. **按甲方项目就绪时间接入。** 自然对流按第 2.1 节先做静水和受控温差。机械搅拌先做规定桨运动的等温短跑，随后再接加热。两个项目分别就绪、分别接入。四环源独立验证。甲方预设齐备后完成四格工程验收。

**第一轮软件完成标志**：Linux NVIDIA GPU 和 Windows SYCL CPU 都能从各自的开发包运行真实回归算例，并在桌面查看结果。**甲方工程验收完成标志**：两套甲方工况按第 2.1 节通过定性检查，并在两平台使用实际发行包复测。
